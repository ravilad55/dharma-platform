# Slice 1 Authentication Architecture

Status: design only, no authentication implementation
Date: 2026-09-10
Scope: Dharma Customer mobile application and the Identity module in the modular monolith.

## 1. Decisions

- Dharma backend is the authority for identity, OTP validity, authentication state, authorization, sessions, and token validity.
- Phone OTP is the only V1 sign-in mechanism. Email association and social authentication are deferred.
- Firebase may be used for messaging infrastructure only; it is not an authentication authority.
- Identity owns users, customer identity state, OTP challenges, sessions, refresh-token families, audit/security events, and the customer authentication policy.
- Customer role/scope is established by the server. Partner and Admin roles are future authorization subjects and are not exposed by the customer mobile flow.
- Access tokens are short-lived JWTs. Refresh tokens are opaque, single-use, rotated, hashed at rest, revocable, and bound to a server session/device record.
- The mobile app stores only the refresh/session material required for recovery in platform secure storage. It never persists tokens in ordinary preferences, logs, or Zustand.
- All auth APIs use `/api/v1/auth`; errors use RFC 7807 ProblemDetails with stable codes and correlation IDs.

## 2. Trust boundaries

The mobile client is untrusted. It may submit a phone number, OTP, refresh token, and device metadata, but it cannot assert user identity, customer role, OTP validity, session validity, or authorization. The API validates every protected request and resolves ownership from server-side records.

Identity is a module inside the modular monolith:

```text
API/composition -> Identity.Application -> Identity.Domain
                                      ^
                         Identity.Infrastructure implements ports
```

`Identity.Domain` has no infrastructure/API dependency. `Identity.Application` depends on domain and shared ports only. SMS, clock, token signing, hashing, persistence, rate limiting, and secure provider adapters are infrastructure concerns.

## 3. End-to-end flow

```text
App launch
  -> session bootstrap reads secure refresh material
  -> POST /auth/refresh if material exists
  -> GET /auth/me to hydrate server identity
  -> authenticated navigation when both succeed
  -> public Login when no valid session exists

Login
  -> validate phone locally for UX only
  -> POST /auth/request-otp
  -> display cooldown and OTP entry
  -> POST /auth/verify-otp
  -> receive access token and refresh token/session metadata
  -> write refresh material to SecureStore
  -> keep access token memory-only
  -> GET /auth/me
  -> authenticated Home
```

Failure paths:

- Invalid local input: no request; show field validation.
- 422 server validation: show safe field errors.
- 429: preserve phone, show server retry time, disable resend until permitted.
- Provider failure: return a generic retryable ProblemDetails response without revealing account existence.
- Wrong/expired/blocked OTP: remain on OTP screen with bounded attempts and safe error code.
- Verify succeeds but network fails after the server commits: bootstrap/retry with the returned session only if the client received it; otherwise request a new OTP. The server remains authoritative and duplicate verification is safe.
- Refresh fails with expired, revoked, or reused session: clear secure material, clear customer query state, and route to Login.
- Logout: revoke the current session server-side, clear secure storage and customer-scoped cache regardless of network outcome; a later request receives 401.

## 4. Token and session authority

### Access token

- JWT, short lifetime configured per environment; proposed initial default is 10 minutes pending security approval.
- Issuer, audience, signing algorithm, key rotation, and clock skew are configuration, never source constants.
- Claims: `sub` user ID, `sid` session ID, `role` coarse customer role/scope, `iat`, `exp`, `jti`, issuer, audience.
- No phone number, OTP, refresh token, address, payment data, or mutable authorization detail is placed in the token.
- API authorization rechecks account/session status and resource ownership where required; a JWT is not a substitute for database authorization.

### Refresh token

- Opaque random value generated by the backend.
- Only a cryptographic hash and token metadata are persisted.
- One active token node per rotation step; presenting a valid token consumes it and creates its replacement in one transaction.
- Reuse of a consumed token revokes the entire token family/session and creates a security audit event; the client must return to OTP login.
- Lifetime, idle lifetime, and grace behavior are configuration. Proposed initial defaults are 30 days absolute and 7 days idle, pending approval.
- Refresh requests are serialized per session/device using a database concurrency rule and, where needed, a short Redis admission lock. A second identical concurrent request must not create two valid successors.

### Session states

`ACTIVE -> REVOKED`, `ACTIVE -> EXPIRED`, `ACTIVE -> SECURITY_REVOKED`; terminal states do not return to active. Expiration is server-derived from absolute/idle limits. Logout is `REVOKED`. Reuse detection or administrative/security response is `SECURITY_REVOKED`.

## 5. Identity database foundation

MySQL is authoritative. All IDs are application-generated opaque UUIDs, timestamps are UTC, and mutable records carry `created_at`, `updated_at`, and `row_version` where concurrency matters. API DTOs are separate from persistence entities.

### `users`

- Primary key: `id` UUID.
- Fields: `phone_normalized` unique, `phone_lookup_hash`, optional `email_normalized` unique, `status`, optional `display_name`, `created_at`, `updated_at`, `created_by`, `updated_by`, `row_version`, `deleted_at` where approved.
- Relationships: one customer profile and many sessions; role membership is through `user_roles`.
- Constraints/indexes: unique normalized phone; nullable unique normalized email; status index; never expose lookup hashes or internal risk metadata.
- Security: phone values are PII; encryption/access control and retention follow the approved privacy policy.

### `customer_profiles`

- Primary/foreign key: `user_id` UUID to `users.id`.
- Fields: customer-specific profile/preferences that are justified by the customer requirements, plus lifecycle timestamps and `row_version`.
- Constraint: one profile per user; no authentication secret fields.

### `otp_challenges`

- Primary key: `id` UUID; foreign key to `users.id` nullable until first successful verification.
- Fields: normalized phone lookup hash, OTP digest, challenge state (`REQUESTED`, `SENT`, `VERIFIED`, `EXPIRED`, `FAILED`, `LOCKED`, `SUPERSEDED`), `expires_at`, `consumed_at`, `superseded_at`, `locked_at`, `attempt_count`, `provider_delivery_reference`, device hash, risk bucket, correlation ID, `created_at`, `updated_at`.
- Constraints/indexes: index `(phone_lookup_hash, created_at)`, index `(device_hash, created_at)`, index `(state, expires_at)`, and a transactionally enforced latest-active challenge rule. OTP digest is never returned or logged.
- Lifecycle/retention: short-lived challenge content is purged after the security retention window; aggregate audit outcomes may be retained separately without OTP material.

### `sessions`

- Primary key: `id` UUID; foreign key `user_id` to `users.id`.
- Fields: `family_id`, device identifier hash, platform/app version, state (`ACTIVE`, `REVOKED`, `EXPIRED`, `SECURITY_REVOKED`), `created_at`, `last_seen_at`, `expires_at`, `revoked_at`, `revoked_reason`, IP/risk metadata where approved, `row_version`.
- Relationships: one user has many sessions; one session has many refresh-token rotation nodes.
- Indexes: `(user_id, state, last_seen_at)`, `(family_id, state)`, and device/session lookup. No raw device hardware identifier is required.

### `refresh_token_nodes`

- Primary key: `id` UUID; foreign keys `session_id` and `user_id`.
- Fields: `family_id`, cryptographic `token_hash` unique, `issued_at`, `expires_at`, `consumed_at`, `revoked_at`, `replaced_by_node_id`, `reuse_detected_at`, `created_at`.
- Constraints: unique token hash; only one successful consumer of a node; replacement and consumed timestamps are written atomically; a reused node revokes its family/session.
- Security/retention: never store plaintext tokens. Retain revoked/consumed metadata for the approved security investigation period, then purge or pseudonymize.

### `user_roles`

- Composite primary key: `(user_id, role_id)` with foreign keys to `users` and `roles`.
- V1 customer authentication grants only the approved customer scope. Partner/Admin roles remain separate future policy data and are not accepted from client claims.

### `roles`

- Primary key: `id` UUID; unique stable `code` such as `CUSTOMER`.
- Role changes are audited and server-authorized.

### `auth_audit_events`

- Primary key: `id` UUID.
- Fields: event type, opaque actor/user/session/challenge IDs, outcome, reason category, correlation ID, occurred-at UTC, safe metadata, retention classification.
- Indexes: `(user_id, occurred_at)`, `(event_type, occurred_at)`, `(correlation_id)`.
- Security: no OTP, token, authorization header, full phone, provider body, or secret.

Database transaction requirements:

1. OTP verification increments/locks/consumes the challenge and creates or resolves the user/session atomically.
2. Refresh rotation consumes one token node and inserts its successor atomically with a uniqueness/concurrency guard.
3. Logout changes session state idempotently and writes its audit/outbox record in the same transaction where required.
4. Refresh reuse revokes the family/session and records the security event atomically.

## 6. OTP provider boundary

Application depends on `IOtpProvider` with operations equivalent to `SendAsync(destination, messageContext, cancellationToken)` and a provider result that does not contain a plaintext OTP in logs or events. The provider adapter is infrastructure-owned.

For local development, a clearly named `DevelopmentOtpProvider` may return a test delivery result only when an explicit development environment and opt-in configuration are both present. It must refuse to start in production and must never log a real OTP. Production uses an approved SMS provider selected later; vendor choice is not part of this design.

## 7. Configuration policy

The following are configuration-backed policy values, not hardcoded business constants:

- OTP lifetime and maximum verification attempts.
- Resend cooldown, maximum requests per phone, IP, and device windows.
- Lock duration and challenge supersession behavior.
- Access-token lifetime, issuer, audience, signing key reference, and clock skew.
- Refresh absolute/idle lifetime, family reuse response, and session limits per user/device.
- Phone normalization region policy and allowed number formats.
- Development provider enablement.

Product/security approval must set production values before implementation. The server returns only safe expiry/cooldown metadata, never policy secrets or internal rate-limit keys.

## 8. Authorization foundation

Customer authentication establishes a user subject and customer scope. The initial policy is `CustomerAuthenticated`; it permits only customer-owned resources and excludes partner/admin operations. Future partner roles are modeled separately through organization memberships. A client-supplied role is ignored. Every resource handler performs server-side ownership/policy checks.

## 9. Events and audit

Domain/integration events only represent durable state changes: `UserRegistered`, `UserAuthenticated`, `SessionCreated`, `SessionRevoked`, and `UserDeactivated` are candidates subject to implementation review. `OtpRequested`, delivery failure, invalid OTP, rate-limit, refresh reuse, and suspicious session activity are operational security/audit events unless a later requirement makes them integration events.

Outbox events contain IDs, event type/version, timestamps, correlation/causation IDs, and safe metadata. They never contain OTPs, tokens, authorization headers, secrets, or full phone numbers.

## 10. Decisions required before coding

- Security-approved numeric policy values and phone normalization region policy.
- Approved SMS provider and sender/compliance requirements.
- JWT signing key algorithm, KMS/Secrets Manager reference, rotation process, and issuer/audience values per environment.
- Whether a user record is created at OTP verification for a first-time number or via a separate customer onboarding command; the API contract below assumes verification can create the customer identity atomically without exposing registration as a separate auth flow.
- Device/session maximums and account recovery/support policy.
